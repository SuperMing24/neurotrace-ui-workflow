# 版本治理

展示编号、源码提交、Git tag、GitHub Release、Vercel 部署和数据库状态分别登记，不互相替代。

## 已有历史

- `review/catalog.json` 与 `history/<版本>/manifest.json` 是既有前端回看证据，共 24 份。原始页面在 `screen.txt`，通过共享入口加载并隔离网络和本机进度。
- `manifest.meta.original` 只在原材料提供部署 URL 时填写。空值保持空值。归档可能包含原交付已做的私信脱敏或链接改写，不能称为当时生产服务和数据库的完整复制。
- GitHub 基线有 37 个提交；各版可能对应多个提交，V2.x 曾独立交付而未同步到 GitHub。索引中的 Git 线索只表示源码存在，不冒充部署绑定。
- 没有旧 tag 和 GitHub Release。本轮不回填、倒签或给“V1.6”补造正式 Release。

## 本轮工程整理

保留原 `release.json` 的 `2.3.0` 和全部历史 manifest。只把共享评审控件移动到工作流栏，记录在 CHANGELOG 的未发布条目。`review/` 共享外壳本就不属于冻结的游戏文件，因此归档原字节和严格源文件校验仍可保持通过。公共仓库仍未推送这轮改动。

## 未来一般维护

普通文档／共享评审界面修订可以是未发布提交；描述应说明“无游戏版本变化”。任何 push／PR 前先检查 Git 与 Vercel 的自动构建关联，确认不会违反当前不部署约束。不要为赶齐版本列表把所有内容只归为一个没有来源的大 ZIP。

## 未来正式版本（需要单独发布授权）

1. 先完成维护变更、许可和数据审查、离线检查、隔离环境验收及评审，确定具体源码提交和发布目标。
2. 游戏本体或素材确需迭代时再选新编号，更新当前版本记录，只创建新的归档目录。旧编号和清单禁止覆盖。
3. 运行原有冻结／严格校验工具，确保最新前端与新归档一致；运行测试和公开文件清单检查。
4. 在发布记录中保存 commit、tag（若采用）、Release URL（若创建）、来源包哈希、部署 ID／URL、环境、数据库迁移证据与验收结果。tag／Release 是单独动作，不由构建脚本隐式执行。
5. 发布预览和生产均需处于用户已授权的范围。GitHub 同步、Vercel 关联、迁移与发布拆开实施；生产回滚不自动回滚数据库或账本。

目前没有新增会自动发布的 GitHub Actions 或部署钩子。本轮的本地构建工具只复制已核验输入，不修改 `release.json`、写 `history/`、创建提交、打 tag 或调用云服务。
